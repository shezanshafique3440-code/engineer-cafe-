# Cafe hardening release review

This release was verified locally using disposable test databases. Verification did not deploy to the VPS, migrate or seed a live database, send live email, or take a payment. The existing staff/profile capabilities, cafe data, menu and business workflows are preserved. The additive migration changes only auth/session metadata, order attribution, password-reset records and indexes; it does not backfill guessed historical cashier names.

## Changed behavior

- Order numbers and UUIDs no longer reveal guest customer details. A signed receipt link lasts 30 days and returns an explicit allowlist of bill/progress fields. Account owners and authorized staff retain private order access; waiter scope and custom permissions apply. Existing unsigned guest receipt links require authorized sign-in; new receipts contain the protected link. Losing or forwarding a receipt link gives access to the public bill/progress only. The link is a bearer capability: keep it private.
- Password changes and resets revoke old JWT sessions. Logout revokes all sessions for the same account; the two owners should each use their own account. A network failure cannot pretend to have signed the user out. Old tokens without a version remain accepted only while the account's session version is 0; changing the password or signing out invalidates them.
- Normal counter bills stay on the familiar online page. The draft (items, options, notes, customer, cash and UUID) transfers to the prepared offline shell on an outage. Native offline drafts survive reload. Credit, approval-discount and non-drawer-account drafts stay preserved for online completion rather than silently changing payment terms.
- Before submission, counter/table/web checkout stores the exact request. Counter requests also retain their original quoted line amounts for provisional receipts. An uncertain response is recovered with the same payload and UUID; the UI locks editing until confirmation. The offline outbox can retain an original online POS request without converting its payload to the offline protocol. Authentication failures retain pending records. Prepare the browser and an open cash shift while online; offline sync still requires that original cashier/shift to remain valid.
- New orders store cashier attribution; payments also store their shift and cashier. Offline device capture time is a separate report column; server receipt/posting timestamps remain authoritative. Historical cashier/capture fields stay empty where unknown.
- Authorized cashiers/owners can preview then edit quantities/notes/remove items on unpaid, unprepared, undiscounted tickets. The server re-prices, adjusts product/ingredient reservations atomically, checks version/stock and audits the change. Paid, prepared, credit, coupon and loyalty bills require the existing cancellation/reconciliation flow. This editor does not add new products to an existing ticket; create a separate ticket for extra items.
- Reports include cashier/capture columns and payment reversal metadata plus active amount. Exports run in an isolated child process with a 768 MB JavaScript heap, 50-second timeout and 50 MB download ceiling. They reject more than 50,000 rows per sheet or 150,000 source rows with a clear request for a smaller date range. Data is never silently truncated. The web process avoids Excel serialization CPU/heap spikes; this is a bounded single-VPS export implementation, not a persistent background export queue.
- Business reads use read-only consistent snapshots without the global write lock. Employee/customer/supplier/drawer balances and rider summaries use grouped queries. New journal/order/purchase indexes support the actual relation lookups.
- Dashboard order-value charts are explicitly distinguished from posted accounting revenue. Date filters use Pakistan calendar days. Inactive-category products cannot be listed, quoted or opened publicly. Oversized JSON/multipart requests, cross-site mutations, fake images, oversized decoded images and optimizer SVG requests are rejected. Uploads become stripped/re-encoded WebP images. Printing a logo has a timeout.
- Online checkout is disabled until a real payment provider and verified webhook implementation are selected. Existing cash, COD, bank/wallet ledger operations remain available. This release does not claim a working online gateway.
- Password recovery UI/API supports expiring hashed single-use reset tokens with Resend. Set `RESEND_API_KEY`, `RESET_EMAIL_FROM` and the correct canonical `NEXT_PUBLIC_SITE_URL`; verify the sender/delivery before handover. Without configuration the UI clearly asks the user to contact the owner. No live email was sent during tests.
- System health is owner-only at `/admin/system`; public `/api/health` checks the database without exposing diagnostics. Background push notifications apply the same profile/custom/waiter scope as order reads. Unexpected API failures carry a request reference and structured server log.
- Seed refuses nonempty databases, and production initial seed additionally needs explicit opt-in. Deployment rollback preserves the previous dependencies as well as code/build. Backups pause all cafe writers, can transfer an integrity-protected encrypted offsite copy, and publish a verified health marker. Dynamic metadata/manifest use the configured cafe name.

## Verification and operational limits

Run `npm ci`, `npm run lint`, `npm run typecheck`, `npm test`, `npm run build`. `npm run test:integration` drops/recreates **only** the explicitly named localhost `cafe_operations_test` database, applies migrations and runs isolated finance, permission, delivery, offline, report and hardening suites. Set a disposable `DATABASE_URL`, strong test `AUTH_SECRET` and optionally `CAFE_TEST_CHROMIUM`. Playwright and PostgreSQL test dependencies are declared; `.github/workflows/quality.yml` runs these checks with Node 22/PostgreSQL 16. Local verification does not establish a successful GitHub Actions run; check the release commit’s workflow status separately.

Use the reviewed proxy header/body-limit sample in `deploy/nginx-cafe-location.conf` when deploying. Rate limiting is process-local and assumes Nginx overwrites `X-Real-IP`. Keep the supported single cafe app process; a multi-instance deployment needs a shared limiter and coordinated export admission control. No production Nginx changes were performed here.

For optional offsite backups, configure the root-only backup service environment: `CAFE_OFFSITE_DEST=user@host:/absolute/path`, `CAFE_BACKUP_PASSPHRASE_FILE=/root/private-passphrase-file`, and install GnuPG/OpenSSH. Pre-register the destination SSH host key and use a restricted backup account. Test a decrypt/restore drill on an isolated database. The script never deletes local backups; retention and storage alerts must be configured for the selected offsite service. A successful copy is not a substitute for a restore drill.

Before live handover, verify the existing AUTH_SECRET is random and at least 32 characters, backup/restore, HTTPS/actual Nginx headers, payment-provider choice, recovery email, PM2 worker health, the physical receipt printer and a real router disconnect/reconnect on the client's device. Those external checks cannot be certified from this local environment. A numeric 10/10 guarantee would overstate the evidence.
